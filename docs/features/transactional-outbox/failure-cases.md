# Transactional Outbox — Failure Cases, Attack Vectors & Mitigations

This document catalogs critical failure modes, race conditions, edge cases, and mitigations for the Transactional Outbox pattern implemented across PostgreSQL 18 and Apache Kafka 4.4.

---

## 1. Failure Modes & Resilience Matrix

| Failure Mode ID | Scenario / Trigger | Immediate Impact | Invariants Challenged | Architectural Mitigation & Detection |
|---|---|---|---|---|
| **FAIL-OX-001** | Relay crashes after Kafka produce ACK but *before* updating `status = 'PUBLISHED'` in PostgreSQL. | Message is republished upon relay restart or lease expiry, resulting in duplicate delivery to Kafka. | **OX-03, OX-06** | **Mitigation:** Consumer idempotency via Inbox Deduplication (`inbox_messages` table with primary key `(tenant_id, event_id)`). The relay guarantees *at-least-once*; consumers must enforce *exactly-once* semantics. |
| **FAIL-OX-002** | Payload exceeds Kafka `max.request.size` (e.g. 1 MB) or fails broker schema registry validation. | Relay worker fails to publish; repeatedly retrying head-of-line row blocks all subsequent events for that partition key or table. | **OX-07, OX-09** | **Mitigation:** Pre-commit validation. Payloads larger than 512 KB are uploaded to object store (S3/GCS/MinIO) and replaced with an opaque claim check reference (`claim_check_url`). If an invalid payload slips through, attempt counter increments to 5, moves record to `status = 'PARKED'`, and fires a P1 alert. |
| **FAIL-OX-003** | Gap in sequence numbers due to rolled-back business transactions when using PostgreSQL sequences (`nextval`). | Downstream consumers expecting strictly gapless sequence numbers stall waiting for missing sequence. | **OX-02, E3.1** | **Mitigation:** Sequence numbers must NOT be drawn from database sequence objects (`SERIAL`/`BIGSERIAL`). Sequence numbers are generated by locking the parent `saga_instances` row (`SELECT current_sequence FROM saga_instances WHERE id = $1 FOR UPDATE`) and incrementing inline. |
| **FAIL-OX-004** | Hot saga generating 200+ step events in a single fork transaction causing transaction bloat and relay lock contention. | Elevated WAL generation, long-lived PostgreSQL transactions, replica lag, and memory pressure on poller. | **OX-01, E3.3** | **Mitigation:** Bounded transaction sizes. Fork dispatch writes are chunked in batches of 50. The relay processes messages with batch size `LIMIT 100` and stream-publishes per partition key asynchronously. |
| **FAIL-OX-005** | Database connection loss at the exact moment of `COMMIT`. Client cannot determine if transaction committed. | Client receives 500/timeout and may retry, risking duplicate saga initiation and outbox entries. | **OX-01, E3.4** | **Mitigation:** Enforce business idempotency on saga initiation: `UNIQUE (tenant_id, workflow_id, external_id)`. Upon retry, query whether the saga exists; if yes, return existing saga status instead of creating duplicate outbox records. |
| **FAIL-OX-006** | Relay crash while holding lease on 500 rows (`IN_FLIGHT`). Other pollers skip these locked/claimed rows. | Outbox events remain unforwarded until lease timeout expires, causing artificial latency spikes. | **OX-06, Mode B** | **Mitigation:** Dynamic lease expiry (`lease_expires_at = NOW() + INTERVAL '30 SECONDS'`). Background sweeper worker or standard query filter selects `WHERE status = 'PENDING' OR (status = 'IN_FLIGHT' AND lease_expires_at < NOW())`. |
| **FAIL-OX-007** | Kafka broker outage or partition reassignment (KRaft metadata sync delay). | Poller connection buffer fills; outbox table grows rapidly; risk of disk exhaustion if storage is unmanaged. | **OX-05, OX-09** | **Mitigation:** Circuit breaker trips after 3 consecutive produce timeouts. Poller backs off exponentially with full jitter up to 30 seconds. Prometheus alert `OutboxPendingRowsHigh` triggers when pending rows exceed 5,000. Disk threshold alarms alert at 80% storage. |
| **FAIL-OX-008** | Table bloat caused by accumulated `PUBLISHED` rows under high throughput (e.g. 5k msgs/s). | Degraded index scan performance on `outbox_events`, higher maintenance overhead on autovacuum. | **OX-10** | **Mitigation:** Range partitioning on `created_at` (e.g., daily partitions). Partitions older than 7 days that contain zero `PENDING` or `PARKED` records are detached and dropped concurrently (`DROP TABLE`). |

## 2. In-Depth Failure Drill Scenarios

### Drill 1: The Relay Crash (Duplicate Publish Verification)

```mermaid
sequenceDiagram
    autonumber
    participant R1 as Relay Instance 1
    participant DB as PostgreSQL 18
    participant K as Kafka KRaft
    participant R2 as Relay Instance 2
    participant C as Downstream Consumer

    R1->>DB: SELECT * FROM outbox_events WHERE status = 'PENDING' FOR UPDATE SKIP LOCKED
    DB-->>R1: Return row ID 88a1 (Event: StepDispatched)
    R1->>DB: UPDATE outbox_events SET status = 'IN_FLIGHT', lease_expires_at = NOW() + 30s
    R1->>K: Produce message (event_id: 'evt-88a1', key: 'tx-42')
    K-->>R1: Broker ACK (Offset 10452)
    Note over R1: CRASH (SIGKILL / OOM before DB status update)
    
    K->>C: Consumer receives evt-88a1
    C->>C: Execute business mutation + insert inbox record (evt-88a1)
    
    Note over DB: 30 seconds elapse; lease expires
    R2->>DB: SELECT * FROM outbox_events WHERE status = 'IN_FLIGHT' AND lease_expires_at < NOW()
    DB-->>R2: Return row ID 88a1
    R2->>K: Produce duplicate message (event_id: 'evt-88a1', key: 'tx-42')
    K-->>R2: Broker ACK
    R2->>DB: UPDATE outbox_events SET status = 'PUBLISHED', processed_at = NOW()
    
    K->>C: Consumer receives duplicate evt-88a1
    C->>C: Query inbox: evt-88a1 already processed
    C-->>C: Discard without side-effect (IDEMPOTENT NO-OP)
```

## 3. Runbook & Operator Intervention for Poison Messages (`PARKED`)

When an outbox event enters `PARKED` status due to unrecoverable serialization or broker rejections:

1. **Query parked records:**
   ```sql
   SELECT id, transaction_id, event_type, attempt_count, last_error_class, created_at
   FROM outbox_events
   WHERE status = 'PARKED'
   ORDER BY created_at ASC
   LIMIT 10;
   ```
2. **Inspect payload and failure reason:**
   ```sql
   SELECT payload, last_error_message
   FROM outbox_events
   WHERE id = '88a1e54c-7c09-4c8d-8c11-d7f999999999';
   ```
3. **Remediation Options:**
   - **Fix payload in-place:** Update corrupted fields, reset status:
     ```sql
     UPDATE outbox_events 
     SET payload = '{"corrected": true}', status = 'PENDING', attempt_count = 0 
     WHERE id = '88a1e54c-7c09-4c8d-8c11-d7f999999999';
     ```
   - **Discard if superseded:** Mark as `DISCARDED` with operator audit trail log.
